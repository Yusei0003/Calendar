## 0. このドキュメントの使い方

仕様は次の順で固めます。上から順に、**後戻りのコストが高い順**に並んでいます。

| 順 | 決めること | 状態 |

| 1 | 誰がどうやって入るか（認証・名乗り方） | 方針決定済 → 1章 |
| 2 | 「予定1件」が持つ情報（データモデル） | ドラフト → 2章 ★ |
| 3 | 画面と操作（何ができるか） | ドラフト → 3章 ★ |
| 4 | 見た目の方向性 | ドラフト → 4章 ★ |

| 6 | 作る順番 | ドラフト → 6章 |

2〜4章が固まればそのまま実装に入れます。

## 1. 認証・利用者

### 決定事項

- **入り方: スタッフ全員で共通の合言葉（パスコード）1つ**
- 人数規模: 〜10人
- 端末: PC・スマホ両方（どちらも常用）

### 合言葉方式の補強（重要）

合言葉だけだと「誰が登録・変更したか」が残らず、予定の持ち主も指定できません。そこで **2段構え** にします。

1. **合言葉を入力** → アプリに入れる（アクセス制御）
2. **「あなたは誰？」でスタッフ名を選ぶ** → 端末に記憶（名乗り）

名乗りはパスワードではないので、なりすまし防止にはなりません。あくまで
「自分の予定をすぐ出す」「更新履歴に名前を残す」ための仕組みです。
※後から Google ログインへ移行できるよう、スタッフ情報は最初から独立したテーブルで持ちます。

### セキュリティ上の設計判断

- 合言葉は**ブラウザ側で照合しない**。Next.js のサーバー側で照合し、成功したら
  httpOnly Cookie（署名付き・有効期限30日）を発行する。
- データベースへのアクセスは**すべてサーバー経由**。ブラウザに DB のキーを置かない。
- 合言葉はハッシュ化して環境変数で管理。変更したい時は環境変数の差し替えのみ。
- 5回連続で失敗したら同一IPを15分ロック（総当たり対策）。
- ★確認: 合言葉の文字列（後で決定でOK。運用開始時に設定）
- ★確認: 合言葉を変更したら全員ログアウトさせる運用でよいか

## 2. データモデル ★要確認

### 2.1 スタッフ（staff）

| 項目 | 内容 |
|------|------|
| 名前 | 表示名（例: 佐藤） |
| 色 | この人の予定に使うアクセントカラー |
| 並び順 | 一覧での表示順 |
| 在籍中か | 退職者は非表示にするが過去の予定は残す |

★確認: スタッフの初期メンバー（名前だけで可）。部署・店舗の区分は必要か。

### 2.2 予定（events）

用途が「スタッフの予定共有」と「イベント・営業スケジュール」の2つなので、
**1つのテーブルに `種別` を持たせて** 区別します。

| 項目 | 必須 | 内容 |
|------|------|------|
| 種別 | ● | `スタッフ予定` / `全体予定`（イベント・営業） |
| 担当スタッフ | 種別による | スタッフ予定なら必須、全体予定なら任意（複数可 ★） |
| タイトル | ● | 例: 「◯◯様 打合せ」 |
| 開始 / 終了 | ● | 日時。タイムゾーンは日本時間固定 |
| 終日フラグ | ● | ONなら時刻を持たない |
| 分類 | ● | 下記の分類から選ぶ |
| 場所 | | 自由入力 |
| メモ | | 自由入力（複数行） |
| 登録者 / 更新者 | ● | 名乗ったスタッフ名を自動記録 |

**分類（ラベル）案** ★要確認 — ここが色分けの軸になるので、実際の業務語に合わせたい:

- 出勤 / 休み / 外出 / 来客・打合せ / 会議 / 納品・配送 / イベント・催事 / その他

★確認: この分類でよいか。増減・言い換えがあれば。
★確認: 色分けは「スタッフごと」と「分類ごと」どちらを主にするか（推奨: スタッフごとを主、分類はアイコン・細い帯で表現）

### 2.3 繰り返し予定

毎週の定例などをどうするか。

- **v1: 繰り返しなし**（1件ずつ登録。コピー機能でカバー）
- **v2: 毎日 / 毎週 / 毎月 + 終了日** に対応

★確認: v1 の時点で繰り返しが必須かどうか。必須なら実装工数が1.5倍程度増えます。

### 2.4 削除の扱い

削除は**論理削除**（実際には消さずに隠す）。誤操作の復旧ができます。

## 3. 画面・機能 ★要確認

### 3.1 画面一覧

| 画面 | 内容 |
|------|------|
| 入場 | 合言葉入力 → スタッフ名を選ぶ |
| 月表示 | 1か月の俯瞰。PCの既定表示 |
| 週表示 | 縦が時間・横が日付のタイムライン |
| 日表示 | 1日をスタッフ別の列で表示（誰が今日何をしているか） |
| リスト | 今日以降の予定を時系列で。**スマホの既定表示** |
| 予定の追加・編集 | 下からせり出すパネル（スマホ）／右サイドパネル（PC） |
| スタッフ管理 | 名前・色・並び順の編集 |

### 3.2 共通の操作

- 上部にスタッフのアイコンを並べ、**タップで絞り込み**（「佐藤さんの予定だけ」）
- 分類でも絞り込み
- 「今日」に戻るボタン、左右スワイプ／矢印キーで前後の月・週へ
- 空いている枠をタップ → その日時で新規作成が開く
- PCではドラッグで予定の移動・時間の伸縮（★ v1 で必要か確認）
- 予定の複製（「同じ内容で別の日に」）

### 3.3 やらないこと（v1 のスコープ外）

明示的に外します。必要なら v2 以降で。

- 予定の承認フロー、シフトの自動組み
- 外部カレンダー（Google カレンダー）との双方向同期
- 通知（メール・LINE・プッシュ）★ 欲しい場合は要相談
- 添付ファイル
- コメント・チャット機能

★確認: 上記のうち v1 に引き上げたいものはあるか（特に通知）

## 4. デザイン方向性 ★要確認

「かっこいい感じ」の解釈を1つに決めます。**提案: A案**。

- **A案 ダーク × ネオン**: 濃紺〜黒の背景に、スタッフごとの鮮やかなアクセントカラー。
  細いグリッド線、なめらかなアニメーション。予定が光って見える。夜間・店内でも目に優しい。
- **B案 ライト × ミニマル**: 白基調、余白広め、細身のフォント。Apple のカレンダー寄り。
  清潔感重視。日中の事務所で見やすい。
- **C案 両対応**: 端末の設定に合わせて自動切替（実装は少し増えるが現実的）

共通で担保するもの:

- スマホは片手で操作できる（主要ボタンを下部に配置）
- 文字と背景のコントラスト比 4.5:1 以上
- 色だけに頼らず、分類はアイコンでも区別（色覚多様性への配慮）
- 日本語フォントで数字・曜日が詰まって見えないよう調整

★確認: A / B / C のどれか。参考にしたいアプリやサイトがあれば教えてください。

## 5. 技術構成・公開方法（決定事項）

| 領域 | 採用 | 理由 |
|------|------|------|
| フレームワーク | Next.js (App Router) + TypeScript | UI の自由度が高く、サーバー処理も同居できる |
| データベース | Supabase (PostgreSQL) | 無料枠で開始でき、後から認証強化・リアルタイム同期に拡張できる |
| スタイル | Tailwind CSS | 細かいデザイン調整がしやすい |
| 公開先 | Vercel | Next.js との相性。無料枠・独自ドメイン可 |
| 日時処理 | date-fns（tz: Asia/Tokyo 固定） | 軽量。サーバーは UTC 保存、表示時に日本時間へ |

### 更新の反映

v1 は**画面を開いた時・タブに戻った時・30秒ごと**に最新を取得する方式（〜10人ならこれで十分）。
「他の人の編集が即座に画面へ出る」リアルタイム同期は v2 で Supabase Realtime を使って追加可能。

### 運用コスト

Supabase・Vercel とも無料枠の範囲に収まる見込み（10人・月数百件の予定）。
独自ドメインを使う場合のみドメイン代（年 1,500円程度）。

★確認: 独自ドメインは使うか（例: calendar.kesenlarus.jp）。不要なら Vercel の無料URLで開始。
